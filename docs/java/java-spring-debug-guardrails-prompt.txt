Java Spring Boot Debugging Guardrails Prompt (MVC + Lombok + MapStruct + Postgres)

Use this prompt when diagnosing bugs, regressions, performance issues, or production incidents in this repository.

---

You are debugging a Java Spring Boot application.
Follow these guard rails for every debugging task.

This project uses a global ControllerAdvice and a standardized `ErrorResponseDTO` contract. Debugging must respect the existing exception-to-status mappings and error payload structure. Do not introduce ad-hoc error responses while fixing defects.

Primary goals:
1. Reproduce deterministically before modifying code.
2. Classify the failure by layer (controller/service/repository/config/integration/DB).
3. Prove the root cause with evidence (logs, failing test, SQL trace, config diff).
4. Apply the smallest safe fix aligned with architecture and existing patterns.
5. Prevent recurrence with tests or assertions at the correct layer.

Architecture and scope constraints:
1. Only work in these modules unless explicitly told otherwise:
- `client`
- `models`
- `rest`

2. Keep responsibilities intact during debugging:
- Controllers: request/response orchestration only.
- Services: business logic and transactions.
- Repositories: persistence access.
- Mappers: DTO/entity translation.

Required debugging workflow:
1. Triage and reproduce:
- Capture exact failing behavior (endpoint, payload, headers, user flow, timestamps).
- Reproduce with deterministic steps in local/staging before editing code.
- Record expected vs actual behavior.

2. Narrow the failure surface:
- Determine layer first: controller, service, mapper, repository, DB, integration client, configuration.
- Validate assumptions with logs, targeted assertions, and focused queries.
- Avoid broad refactors while root cause is unknown.

3. Instrument safely:
- Add temporary structured logs at key boundaries:
  - Controller entry (path, correlation id, status).
  - Service decision branches.
  - Repository calls and query parameters (no sensitive values).
- Enable SQL logging temporarily if data-layer behavior is suspected.
- Never log tokens, credentials, full PII payloads, or secrets.
- Remove temporary debug noise before finalizing unless it adds durable operational value.

4. Root-cause validation:
- Prove the root cause with a failing test, reproducible script, or clear before/after evidence.
- Confirm why related paths are not impacted.
- If issue is data-dependent, include sample fixtures or migration-safe repro data.

5. Implement minimal fix:
- Prefer smallest change that resolves root cause.
- Reuse existing patterns for exception handling, validation, and mapping.
- Keep transaction boundaries in service layer.
- Maintain Postgres/JPA compatibility and avoid introducing N+1/perf regressions.

5.1 Error handling validation:
- Confirm exceptions flow through ControllerAdvice.
- Reuse existing `ErrorResponseDTO` factory methods.
- Verify correct HTTP status mapping (400 vs 404 vs 409 vs 500 etc.).
- Ensure no internal stack traces or SQL details leak to clients.

6. Regression hardening:
- Add or update tests at the lowest effective level:
  - Unit test for pure business or mapping logic.
  - Integration test for controller/service/repository interactions.
- Add assertions for edge cases that exposed the bug.

6.1 Data and transaction validation:
- Verify transactional boundaries remain in service layer.
- Confirm `@Transactional` semantics (readOnly vs write).
- Validate no new N+1 queries were introduced.
- Check query plans or logs if performance regression is involved.
- Confirm database state consistency before and after fix.

7. Validate end-to-end:
- Re-run reproduction steps and confirm fix.
- Verify non-regression in adjacent endpoints/flows.
- Ensure code remains Spotless-compatible.

Debugging checklist before finalizing:
- Was the issue reproduced with deterministic steps?
- Was the root cause proven (not assumed)?
- Was the failure layer correctly classified?
- Is the fix minimal and architecture-consistent?
- Are errors still routed via ControllerAdvice with correct status mapping?
- Are sensitive fields excluded from logs?
- Were transactions and JPA behavior validated?
- Did I add/update tests covering the failure and key edge cases?
- Did I verify no adjacent regressions or performance degradation?

Output requirements for each debugging task:
1. Reproduction summary:
- Exact steps, inputs, and environment.
- Expected vs actual behavior.

2. Root cause:
- Specific class/method/query/config responsible.
- Why it failed and under what conditions.

3. Fix summary:
- Files/classes changed and why.
- Why this is the minimal safe fix.

4. Validation evidence:
- Tests added/updated and their intent.
- Manual/automated checks run.
- Residual risks (if any).

If root cause cannot be reproduced or isolated, stop and ask for missing signals (logs, payloads, env diffs, versions).
