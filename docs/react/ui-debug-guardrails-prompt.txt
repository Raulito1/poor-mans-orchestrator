UI Debugging Guardrails Prompt (React + Vite + TypeScript + RTK Query)

Use this prompt when diagnosing UI bugs, state inconsistencies, API integration issues, performance regressions, or flaky behavior in this repository.

---

You are debugging a React + Vite + TypeScript frontend with RTK Query and a BFF (Node/Express) layer.

Non‑negotiable principles:
1. Reproduce before modifying code.
2. Prove the root cause category before fixing.
3. Apply the smallest safe fix aligned with existing architecture.
4. Do not introduce new global state, endpoints, or abstractions unless strictly required.
5. Remove all temporary instrumentation before finalizing.

Root cause categories (must classify first):
- Rendering logic (props/state derivation/memoization issues)
- Local vs global vs URL state misuse
- RTK Query cache/invalidation/arg instability
- API/BFF contract mismatch (request/response shape, auth headers/cookies, proxy behavior)
  - Status drift (200 vs 204 vs 4xx/5xx), content-type, compression, CORS
  - Missing/incorrect headers forwarded by BFF (Authorization, cookies, x-request-id, etc.)
  - Env/base URL misrouting (proxy targets, path rewrites, trailing slashes)
- Timing/race condition (effects, async updates, unmounted updates)
- Performance/render loop
- Styling/layout/accessibility regression

Required debugging workflow:

1. Deterministic reproduction
- Capture route, query params, user role/entitlements, feature flags, environment, and exact steps.
- Capture request payload + response body from Network tab.
- Define expected vs actual behavior precisely.
- Reduce to smallest failing scenario.

2. State classification check (mandatory)
- Is this server state? → RTK Query only.
- Should it be shareable/bookmarkable? → URL search params.
- Is it ephemeral UI state? → Local component state.
- Is Redux being used only to avoid prop drilling? → Refactor to feature context.

If state placement is incorrect, fix placement before anything else.

3. RTK Query validation
- Confirm endpoint args are stable (no inline objects causing re-fetch loops).
- Validate cache key matches expectation.
- Verify providesTags/invalidatesTags correctness.
- Confirm stale data is not due to missing invalidation.
- Ensure mutations do not trigger unintended refetch cascades.
- Use selectFromResult if excessive rerenders are observed.

4. Rendering/performance validation
- Check for:
  - Inline object/array props causing identity churn.
  - Missing dependency arrays.
  - Over‑broad dependency arrays.
  - Unnecessary global state subscriptions.
  - Infinite render loops.
- Confirm React DevTools shows expected render frequency.

5. Contract validation (UI ↔ BFF ↔ API)
- Validate request shape matches TypeScript types (query params, path params, body).
- Confirm response schema matches expectations (including 204/empty body semantics).
- Ensure no silent undefined/null drift (backend optional fields, nullability, enum values).
- Confirm auth/session assumptions:
  - BFF owns cookies/session; UI should not persist tokens.
  - Verify 401 vs 403 behavior (unauthenticated vs unauthorized) and UI handling.
- Validate proxy correctness:
  - Path rewrites, base URL, trailing slashes, and query param forwarding.
  - Required headers forwarded (Authorization/cookies when applicable, correlation/request id).
- Validate transport specifics when relevant:
  - content-type + encoding (JSON vs text), gzip/br compression, and CORS preflight.

6. Safe instrumentation
- Add targeted logs only around:
  - Hook inputs/outputs
  - BFF request/response metadata (status code, route, request id, timing)
  - Mutation handlers
  - Invalidation paths
- Never log tokens, cookies, or PII.
- Remove all temporary logs before finalizing.

7. Minimal fix implementation
- Reuse existing hooks/components/endpoints/selectors.
- Do not introduce broad refactors unrelated to the root cause.
- Preserve strict typing; do not introduce `any`.
- Do not copy RTK Query results into Redux slices.

8. Regression hardening
- Add/update tests closest to failure:
  - Component behavior tests
  - Hook tests
  - RTK Query integration/cache tests
- Cover loading, error, empty, and success states.
- Validate URL param behavior if touched.

9. Accessibility + UX validation
- Confirm keyboard navigation and focus management.
- Confirm aria semantics preserved.
- Validate responsive layout if changed.

Debugging completion checklist:
- Was the bug reproduced with clear steps?
- Was the root cause proven (not assumed)?
- Is the state location correct (local vs URL vs RTK vs Redux)?
- Is the fix minimal and pattern‑aligned?
- Are types strict and explicit?
- Are unnecessary rerenders eliminated?
- Are loading/error/empty states correct?
- Are accessibility behaviors preserved?
- Were temporary logs removed?

Output requirements for each debugging task:

1. Reproduction summary
- Route + query params
- Role/feature flags
- Input data
- Expected vs actual

2. Root cause
- Exact file/component/hook/endpoint
- Category classification
- Why it failed

3. Fix summary
- Code change explanation
- Why minimal
- RTK Query cache/tag impact
- State placement validation

4. Validation evidence
- Tests added/updated
- Manual verification steps
- Performance confirmation (if relevant)
- Accessibility confirmation
- Residual risks (if any)

If reproduction is inconsistent, stop and request:
- HAR file
- Payload samples
- Feature flag values
- Environment details
- Screen recording

Do not proceed with speculative fixes.
